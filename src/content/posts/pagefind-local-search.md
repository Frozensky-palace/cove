搜索是静态站点公认的短板——没有服务器，拿什么查？Pagefind 的答案很聪明：**把索引也变成静态文件**。Cove 上线搜索用了它，这篇文章记录完整的接入策略。

## 原理：构建后索引产物

Pagefind 在**构建完成后**运行，扫描 `dist/` 里的 HTML 生成索引：

```json
{
  "scripts": {
    "build:search": "pagefind --site dist"
  }
}
```

这个时机选择带来一个重要性质：索引的内容就是用户实际看到的内容。预渲染、MDX 转换、任何构建期变换都天然包含在内，不需要维护"源文件 → 索引内容"的映射。

产物是一堆小的分片文件（按词哈希切分），搜索时按需拉取命中的分片。对一个几百页的站点，首次搜索通常只需要下载几十 KB——这是它比"把全站文本打包成一个 JSON"的方案优雅的地方。

## 圈定正文：data 属性即配置

不加任何标记的话，Pagefind 会索引整个页面包括页头页脚。Cove 用两个属性划清边界：

```html
<!-- 详情页：只有正文进索引 -->
<article data-pagefind-body>
  <h1 data-pagefind-meta="title">标题</h1>
  ...
  <footer data-pagefind-ignore>标签、转载说明</footer>
</article>
```

策略是**白名单制**：只有三类详情页（文章、笔记、项目）和值守者档案页标了 `data-pagefind-body`，列表页、归档页、关于页一概不进索引——搜索"响应式设计"应该直达那篇文章，而不是给你十个也提到这个词的列表页。当前 42 个页面里进索引的只有 12 个，噪音天然就低。

## 元数据与过滤：让结果可扫读

`data-pagefind-meta` 把页面内的元素抽成结果的元数据：

```html
<time data-pagefind-meta="date">2026-09-10</time>
<span data-pagefind-meta="author">温晚安</span>
```

过滤器则用 `data-pagefind-filter` 标注，Cove 按内容类型分了三类：`类型:文章`、`类型:笔记`、`类型:项目`。搜索弹窗里可以按类型收窄结果，结果行显示标题、日期与作者——这些信息原本就在页面上，标一下就能复用，不需要为搜索单独维护任何数据。

## 中文站点需要知道的一件事

Pagefind 对中文没有词干化（stemming），官方也明确提示了这一点。实际影响：搜索"动效"能命中"动效"，但不会自动关联"动效系统""动效设计"这类扩展词。实践下来对中文站点影响比想象的小——中文词形变化本身少，分词后的精确匹配覆盖了绝大多数场景。真正要避免的是指望它做同义词和语义搜索，那是需要向量化服务的另一个世界。

## 前端：按需加载的弹窗

搜索 UI 是一个 Vue 岛屿（搜索弹窗），但页面上平时**不加载任何搜索代码**：

- 页头只有一个按钮，`Ctrl K / ⌘ K` 打开弹窗；
- 弹窗首次打开时才动态 import Pagefind 的 JS 与 CSS，以及索引分片；
- 无 JS 环境下降级为指向搜索页的原生链接，放在 `<noscript>` 里。

这样搜索的全部成本（脚本 + 索引）只在用户表达搜索意图那一刻支付，首页性能零影响。

## 值得吗

| 方案 | 成本 | 效果 |
| --- | --- | --- |
| Pagefind | 构建链加一步，页面加几个 data 属性 | 本地全文搜索，零后端 |
| 外挂搜索服务（Algolia 等） | 账号、同步、按量计费 | 更强的排序与语义能力 |
| 不做搜索 | 零 | 靠标签和归档硬扛 |

对内容量在几百篇以内的个人站点，Pagefind 是明显的甜点区：接入成本一个下午，维护成本为零，效果对访客而言与"真搜索"无异。等内容多到精确匹配不够用时，再考虑升级也不迟——届时 data 属性标注的元数据可以直接迁移。
