Cove 接入了 Giscus 作为评论系统——评论数据存在 GitHub Discussions 里，不需要自己的服务器和数据库。但比"选哪个服务"更值得记录的是接入方式：把评论做成一个**边界组件**，让站点其余部分完全不感知它的存在与故障。

## 为什么是 Giscus

候选方案里，自建评论后端（多说们已死，自维护成本高）、Disqus（广告与隐私债）、Waline/Twikoo（需要自己部署服务端）之外，Giscus 的筹码是：数据在 GitHub Discussions、用 GitHub 账号登录（对技术读者零摩擦）、完全免费。缺点也明确：读者需要有 GitHub 账号。对一个技术向博客，这个取舍成立。

## 边界组件的四层防御

`CommentProvider.astro` 把全部第三方风险封装在一个组件里，站点在布局里只写一行 `<CommentProvider />`：

**第一层：按需加载。** 评论区进入视口（提前 200px 预热）才注入 giscus 脚本。首屏性能与评论是否存在彻底解耦——没滚到底部的访客一个字节的第三方代码都不用下载。

**第二层：失败占位。** 脚本加载失败或 10 秒超时未见 iframe 时，显示失败占位与重试按钮。评论区挂了不该让页面留下一个空白区域，更不该让正文布局抖动——组件给 host 元素预留了最小高度。

**第三层：主题同步。** 站点切换深浅色时，用 MutationObserver 观察 `<html>` 的主题属性，向 giscus iframe postMessage 同步。没有这一层，切深色模式后评论区会突兀地保持白色。

**第四层：构建期裁剪。** 未配置仓库信息时组件零输出——不是隐藏，是压根不渲染任何 DOM 和脚本。

## 路径映射与域名锁

Giscus 用页面路径映射 Discussion：`/posts/foo/` 的评论存在对应 Discussion 里。这带来两个必须处理的问题：

1. **预览页会污染映射**。草稿预览、PR 预览环境的路径与生产相同，如果评论区在那里也加载，会为同一路径创建错位的 Discussion。处理：草稿与计划发布内容的预览页不渲染评论区；
2. **别的域名能冒用你的仓库**。任何人都可以在他们的页面里嵌你的 giscus 评论。修复在仓库根目录放一个 `giscus.json`：

```json
{
  "origins": ["https://cove.xin"],
  "originsRegex": ["http://localhost:[0-9]+"]
}
```

origins 精确匹配 + 正则放行本地开发，其余来源一律拒绝加载。这个文件从仓库默认分支读取，推送即生效——评论系统终于只为自己的域名服务。

## 客户端路由兼容

站点用了客户端路由（换页不整刷），评论组件随之需要处理两个生命周期问题：初始化挂在 `astro:page-load` 事件（首次加载与每次换页后都触发）；组件用轮询自检 `host.isConnected`，发现已从文档摘除就自行清理——不依赖谁记得来销毁它。

## 小结

评论系统的接入要点不是"能显示出来"，而是：**加载策略不影响性能、故障不扩散到正文、身份映射不被预览污染、域名不被冒用**。这四件事都做完，Giscus 才算真正"接入"而不是"嵌入"。
