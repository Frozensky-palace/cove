个人博客项目提案 v2.0

从数据库驱动的博客应用，收敛为以 Git 为内容事实源的 Astro 静态内容系统。保留现代前端体验与长期扩展能力，同时移除个人博客第一阶段不必要的数据库、认证、自研后台和同步链路。

核心框架 Astro内容源 Markdown / MDX + GitHub 交互 Vue 3 Islands部署 Cloudflare Workers 状态 推荐实施基线更新 2026-09-16
原方案

Database = Source of Truth

Supabase 保存文章正文，并承担 Auth、RLS、Storage 与内容发布链路。

→
新版方案

Git + Markdown = Source of Truth

代码、内容、媒体、历史与发布触发统一进入同一个版本化工作流。

00

先给结论：原方案的前台方向正确，后台边界过重。新版以“静态优先、内容即文件、动态按需”为核心。

01

目标与设计原则

面向单人或小规模维护的技术博客：写作顺畅、加载快速、内容可迁移、维护成本低，并且不会锁死未来。

目标可验证结果优先级
内容长期可保存每篇文章是 Git 中的独立 Markdown/MDX 文件，可 diff、回滚、迁移和离线编辑P0
静态优先公开内容构建为 HTML；首屏不依赖数据库或 API 才能阅读P0
零服务器运维无需 VPS、Nginx、容器编排和自管数据库P0
Web 编辑能力Pages CMS 可直接编辑仓库内容并提交到 GitHubP1
可扩展动态功能通过 Worker / Supabase 独立加入，不改变正文事实源P1
工程可维护类型检查、内容 schema、构建检查和可回滚部署形成闭环P1

六条架构原则

Static First

默认生成静态页面，动态只服务于真正需要的交互数据。

Content as Code

内容、元数据和媒体随代码共同版本化。

One Source of Truth

GitHub 仓库是文章内容唯一事实源，避免双写与同步。

Islands by Need

Vue 只为搜索、主题、可视化等局部交互加载。

Replaceable Services

评论、统计、CMS 通过薄适配层接入，避免页面模板锁定供应商。

Backend on Demand

用户态与动态数据出现后再启用 Supabase。

02

系统架构

两条写作入口在 GitHub 汇合；构建链生成静态站点和搜索索引；第三方服务保持旁路、可替换。

运行时边界

发布时发生

  • 读取并校验内容 schema
  • 生成文章、标签、分类、归档页
  • 优化本地图片和静态资源
  • 创建 Pagefind 搜索索引
  • 上传静态资产到 Cloudflare

访问时发生

  • CDN 直接返回 HTML / CSS / 图片
  • 需要时加载 Vue Island
  • 搜索在浏览器加载 Pagefind 索引
  • 评论按需加载 Giscus iframe
  • 统计发送最小化 RUM 数据
03

技术栈与职责边界

每个组件只承担一种清晰职责；版本采用“当前稳定版 + 锁文件”，不在提案中硬编码易过期的小版本号。

内容层Astro Content Collections加载、schema 校验、查询与类型生成构建失败即阻止无效内容上线

CMSPages CMS基于 GitHub 文件的 Web 编辑界面不创建第二份内容数据库

内容组织约定

  • 一篇内容一个文件；文件名使用稳定、可读的英文或拼音 slug。
  • 图片默认放入 src/assets/posts/<slug>/，由 Astro 处理；无需处理的公共文件放 public/。
  • 文章 URL 不绑定日期，避免修改发布日期导致永久链接变化。
  • 项目、笔记和文章使用独立 collection，避免 frontmatter 变成万能字段集合。
05

内容与数据模型

Content Collections 是正文的类型边界。错误元数据应在构建期失败，而不是上线后静默破坏页面。

文章 Frontmatter

src/content/posts/nilm/diffusion-nilm.md
---
title: "Diffusion Model 在 NILM 中的应用"
description: "讨论生成模型在非侵入式负荷监测数据增强中的使用方式。"
publishedAt: 2026-09-16
updatedAt: 2026-09-16
category: "nilm"
tags: ["NILM", "Diffusion", "Deep Learning"]
draft: false
featured: true
lang: "zh-CN"
cover: "../../assets/posts/diffusion-nilm/cover.webp"
canonicalURL: null
---

正文从这里开始。
字段类型必填规则
titlestring是页面标题与 Open Graph 标题的默认来源
descriptionstring是建议 70–160 个中文字符以内，避免复述标题
publishedAtdate是发布时间；排序主键
updatedAtdate否实质更新时填写，不为格式修改刷新
categoryenum / slug是单一主分类
tagsstring[]是建议 1–5 个，构建时规范化
draftboolean是生产构建必须过滤 true
featuredboolean否仅用于首页精选，不改变排序真相
langlocale是驱动 HTML lang 与 Pagefind 语言分组
canonicalURLURL / null否转载内容指向原始规范地址

Schema 示例

src/content.config.ts
import { defineCollection, z } from 'astro:content';
import { glob } from 'astro/loaders';

const posts = defineCollection({
  loader: glob({ base: './src/content/posts', pattern: '**/*.{md,mdx}' }),
  schema: ({ image }) => z.object({
    title: z.string().min(1),
    description: z.string().min(20),
    publishedAt: z.coerce.date(),
    updatedAt: z.coerce.date().optional(),
    category: z.string().min(1),
    tags: z.array(z.string()).min(1).max(8),
    draft: z.boolean().default(false),
    featured: z.boolean().default(false),
    lang: z.enum(['zh-CN', 'en']).default('zh-CN'),
    cover: image().optional(),
    canonicalURL: z.string().url().nullable().optional()
  })
});

export const collections = { posts };

路由与渲染策略

V1 使用 Astro 默认静态输出。路由能在构建时确定，就不引入按需渲染。

路由输出数据源说明
/SSGposts collection简介、精选、最新文章
/posts/SSGposts collection分页文章列表
/posts/[slug]/SSG单篇 Markdown/MDX正文、目录、评论、相关推荐
/categories/[category]/SSG构建期聚合稳定分类页
/tags/[tag]/SSG构建期聚合标签索引
/archive/SSG构建期排序年度归档
/search/SSG + CSR IslandPagefind index搜索页面壳静态，搜索交互客户端运行
/projects/、/about/SSGcollection / page长期内容
/rss.xml、/sitemap.xmlBuild-time已发布内容发现与订阅
升级规则：未来新增 /api/*、私有页面或用户态后，再让这些路由进入 Worker；公开文章仍保持预渲染。不要为了“可能需要”把全站切到 SSR。
07

写作、CMS 与发布流程

本地写作和网页写作不再是两套系统，它们最终都产生 Git commit，并进入同一条构建链。

路径 A：本地专业写作

01编辑内容VS Code / Obsidian 编写 Markdown 或 MDX
02本地预览验证图片、代码块、链接与样式
03提交 Git文章和媒体作为一个原子变更
04推送 GitHubmain 直发或通过 Pull Request
05自动发布Workers Builds → Astro → Pagefind → Workers

路径 B：Pages CMS 网页写作

01GitHub 登录通过 GitHub App 授权仓库
02选择集合文章、笔记或项目
03编辑与上传表单化 frontmatter + Markdown 编辑器
04保存Pages CMS 直接把文件提交回 GitHub
05自动发布进入与本地写作完全相同的构建链

CMS 配置示意

.pages.yml
media:
  input: src/assets/posts
  output: ../../assets/posts

content:
  - name: posts
    label: 文章
    type: collection
    path: src/content/posts
    format: yaml-frontmatter
    filename: '{fields.slug}.md'
    fields:
      - { name: title, label: 标题, type: string, required: true }
      - { name: slug, label: Slug, type: string, required: true }
      - { name: description, label: 摘要, type: text, required: true }
      - { name: publishedAt, label: 发布时间, type: date, required: true }
      - { name: category, label: 分类, type: string, required: true }
      - { name: tags, label: 标签, type: string, list: true }
      - { name: draft, label: 草稿, type: boolean, default: true }
      - { name: body, label: 正文, type: rich-text }
草稿策略：第一阶段使用 draft: true 并在生产查询中排除；若需要编辑审阅，再启用分支 / Pull Request 工作流。不要为单人博客先开发审批系统。
08

搜索、评论与统计

三项能力都位于正文主链之外：即使服务暂时不可用，文章仍可正常阅读。

Pagefind

在 Astro 构建完成后扫描 dist/，生成静态索引。使用 Extended 发行版对中文进行分词。

  • 仅索引正文与需要的元数据
  • 排除导航、页脚与重复内容
  • 搜索 UI 使用 Vue Island

Giscus

评论存入 GitHub Discussions，不引入评论数据库。

  • 按 pathname 建立映射
  • 进入可视区域后再加载
  • 主题跟随站点切换
  • 通过 CommentProvider 封装

Web Analytics

采用 Cloudflare 的隐私优先 RUM，满足 PV、访客来源与核心性能观察。

  • 默认不做自定义事件
  • CSP 明确允许 beacon
  • 需要漏斗时再评估 Umami

构建命令基线

package.json / scripts
{
  "scripts": {
    "dev": "astro dev",
    "check": "astro check",
    "build": "astro check && astro build && pagefind --site dist",
    "preview": "astro preview"
  }
}
09

SEO、性能与可访问性

静态输出只是起点；元数据一致性、语义结构、链接稳定性和低 JavaScript 才决定长期质量。

SEO

  • 唯一且稳定的 canonical URL
  • title、description、Open Graph、X Card
  • BlogPosting 与 Person JSON-LD
  • RSS、Sitemap、robots.txt
  • 草稿与预览环境 noindex

性能

  • Astro 静态 HTML + 最少 hydration
  • 本地图片尺寸约束与现代格式
  • 字体优先系统栈或自托管子集
  • 评论、代码高亮增强按需加载
  • 以 Core Web Vitals 观测回归

可访问性

  • 语义标题层级与主内容跳转
  • 完整键盘操作与可见焦点
  • 正文对比度、16px 以上基准字号
  • 图片 alt；装饰图片空 alt
  • 尊重 reduced-motion 与系统主题
指标建议门槛说明
构建有效性0 个 schema / type 错误任何无效 frontmatter 阻断生产部署
破损内部链接0迁移或重命名必须加重定向
无交互页面 JS尽可能接近 0普通文章不加载 Vue runtime
Lighthouse四项建议 ≥ 90作为趋势门禁，不把单次波动当绝对真理
布局稳定性图片和嵌入保留尺寸避免内容加载导致跳动
10

安全、备份与运维

删除应用后端后，攻击面显著缩小；剩余重点转向供应链、仓库权限、第三方脚本与内容完整性。

安全基线

  • GitHub 开启 MFA，Pages CMS App 仅授权目标仓库
  • 依赖锁文件提交，自动化更新通过 PR 审阅
  • 不在仓库或前端暴露任何服务端密钥
  • 第三方脚本最小化，并通过 CSP allowlist 管理
  • 安全头：CSP、HSTS、Referrer-Policy、Permissions-Policy、X-Content-Type-Options
  • 预览域名与 workers.dev 别名避免被索引

备份与恢复

  • GitHub 保存代码、正文、媒体和完整历史
  • 定期镜像仓库到本地 / NAS / 第二远端
  • 发布回滚优先回退 commit 并重新部署
  • 域名、DNS、Giscus、Analytics 配置写入运维文档
  • 季度执行一次恢复演练：从空目录重建并发布预览

public/_headers 建议

security headers baseline
/*

12

开发阶段与验收

每个阶段都交付可运行结果，避免同时搭建 CMS、评论、统计和动态后端而失去主线。

Phase 1 · Foundation

Astro、TypeScript、Tailwind、基础 Layout、Content Collections、首页与文章页。验收：至少一篇 Markdown 文章可静态构建和阅读。

Phase 2 · Content System

分类、标签、归档、项目页、RSS、Sitemap、SEO 元数据和图片约定。验收：内容模型被 schema 校验，草稿不进入生产。

Phase 3 · Reading Experience

Pagefind、目录、代码体验、主题、图片灯箱、Giscus、Web Analytics。验收：关掉第三方服务后正文仍完整可读。

Phase 4 · CMS

Pages CMS、媒体配置、GitHub App 权限、网页编辑与草稿工作流。验收：不打开本地编辑器也能新建文章并触发预览。

Phase 5 · Engineering

安全头、链接检查、备份、性能回归、可访问性检查和运维文档。验收：从全新环境可按文档重建并发布。

Phase 6 · Optional Application Layer

仅在业务出现后引入 Worker API、Supabase、R2、邮件或会员系统。验收：动态层故障不影响公开正文。

V1 完成定义

  • 所有公开路由均有真实内容、404 和移动端布局。
  • 文章 frontmatter、内部链接与构建全部通过。
  • GitHub push 能触发预览与生产部署。
  • Pagefind 能检索中文标题与正文。
  • Giscus、Web Analytics 和安全头已按生产域名验证。
  • README 说明写作、发文、回滚与恢复流程。
13

扩展路径与引入阈值

Supabase 保留为能力选项，而不是基础依赖。只有动态数据无法由 Git 合理表达时才加入。

需求信号推荐扩展仍留在 Git 的内容引入前检查

AI 协作指引

这部分可直接作为 Claude Code、Codex 或其他开发 Agent 的项目上下文。目标是让自动化修改遵守架构边界，而非重新引入已删除的复杂度。

必须遵守

  1. GitHub 仓库中的 Markdown / MDX 是博客正文唯一事实源。
  2. 默认使用 Astro 静态输出；没有明确动态需求时不得引入 SSR、数据库或 API。
  3. Vue 只用于需要客户端状态的 Islands；普通布局与文章渲染使用 Astro。
  4. 内容字段必须先更新 Content Collections schema，再更新 CMS 配置与页面消费代码。
  5. 所有生产内容查询必须过滤 draft: true。
  6. 第三方服务必须封装，故障或被移除时不得阻断正文渲染。
  7. 不得在客户端、仓库、日志或示例配置中写入密钥。
  8. 新增依赖前说明必要性、体积影响与替代方案，并保持锁文件同步。

# 项目上下文

这是一个 Git 驱动的 Astro 静态个人博客。

## 核心架构
- Astro + TypeScript + Tailwind CSS
- Vue 3 仅用于局部 Islands
- Markdown/MDX + Astro Content Collections
- GitHub 是代码、内容、媒体和历史的唯一事实源
- Pages CMS 只提供 Git 文件编辑界面
- Pagefind 提供构建期静态搜索
- Giscus 提供可替换的评论层
- Cloudflare Web Analytics 提供基础统计
- Cloudflare Workers Static Assets / Workers Builds 负责部署
- Supabase 仅在未来存储动态应用数据，禁止存储博客正文

## 修改规则
1. 默认保持全站静态；不要无需求引入 SSR 或 API。
2. 新增交互前先判断是否可用 Astro/原生 HTML 完成。
3. 修改内容字段时同步更新 schema、.pages.yml、模板与测试内容。
4. 生产查询过滤 draft；URL 保持稳定。
5. 第三方集成放入 components/integrations，页面只依赖抽象组件。
6. 运行 astro check、build、Pagefind 和链接检查后再交付。
7. 不泄露密钥，不扩大 GitHub App 权限，不绕过安全头。

## 任务输出

禁止行为

  • 把全部页面改成 Vue SPA
  • 把所有 Markdown 无差别改成 MDX

  • 写死 Giscus 或 Analytics 到文章模板深处
  • 把预览域名暴露给搜索引擎
  • 只修改生成目录而不修改源文件

最终决策与实施建议

以新版方案作为实际开发基线；原方案保留为未来“从博客走向内容应用”时的能力参考，而不是第一阶段实现清单。

最终架构一句话：使用 Astro + Markdown/MDX + GitHub 构建以 Git 为内容事实源的静态个人博客，通过 Pages CMS 提供网页编辑，通过 Workers Builds 自动构建并以 Cloudflare Workers Static Assets 全球分发，使用 Pagefind、Giscus 与 Web Analytics 提供搜索、评论和统计，并仅在出现明确动态业务时引入 Supabase。

现在做

静态内容、内容 schema、基础站点、搜索、评论、SEO、自动发布与备份。

出现需求再做

账户、收藏、私有内容、会员、动态评论、结构化业务数据。

明确不做

自研 CMS、为正文建立数据库、全站 SSR、重复 API 层和内容双写。

建议启动顺序

  1. 用真实的 3–5 篇文章验证内容模型，而不是先做完整主题。
  2. 完成首页、文章页、标签/分类、RSS 与 SEO，再接 Pagefind。
  3. 部署到 Workers 并跑通 Git 发布闭环。
  4. 最后接 Pages CMS、Giscus、Analytics 与工程门禁。
  5. 运行一个月后根据真实使用痛点决定是否需要动态层。
